# 从简单想法到可确认的界面

## 先整理，再补问

从会话、用户提供的材料和已授权的只读检查中，提炼六项：谁在什么场景用、当前问题、最重要的 1–3 个任务、必须保留的内容与规则、此次交付物、可观察的完成标准。不要求用户填完表格才开始工作；没有依据的内容分别标为建议、假设或待确认。

每轮最多问三个会实质改变方案的问题，用普通中文给出简明选项。优先问影响任务路径、权限、数据含义或最终交付范围的问题。间距、组件细节等由助手提出建议。可以继续不依赖回答的研究，但不将未回答视为确认。

## 研究到方案

研究当前产品类型与技术约束，通常选 3–5 个相关官方示例、成熟产品或开源项目。每个参考说明学习点与适用边界；不因高 star、截图精美或宣传用语而认定其适用。已有足够研究时复用。无法联网时说明限制，不编造链接、维护状态或已读范围。

给出一个推荐方向。只有存在实质性取舍或用户要求时才提供多个方案。方案包含需求摘要、信息分组、主路径、必要状态、视觉与组件选择、验收标准及假设；表述短而具体，不把完整技术方案灌进产品界面。

## 先确认页面生成提示词

面对一句新的页面想法，研究后先输出完整、可复制、可修改的页面生成提示词。写清使用者与任务、页面模块、内容与状态、视觉规则、关键交互、响应式方向和本次交付，不让用户自行补齐技术细节。将建议、假设与已知事实分开，关键待确认项最多三项。具体要求见 [page-prompt.md](page-prompt.md)。

等待用户确认或补充后再生成示例图；用户补充时将修改合入完整提示词，说明差异。已确认的提示词和明确的局部迭代沿用原批准，不重复整个流程。

UI 预览先生成示例图；重要动效补充可播放演示或交互原型。预览置于独立位置，不改业务实现、配置和目标文档。图片能力不可用时说明限制，提出替代预览供用户选择，不将文字描述冒充图片或已完成交互。

## 确认边界

| 用户反馈 | 可继续做什么 |
| --- | --- |
| “这个想法可以，继续看看” | 继续研究或整理提示词，不跳过尚未完成的提示词确认，也不修改业务实现 |
| “先把提示词中的表格换成列表” | 合并修改，展示完整更新稿，确认改变的范围后再生成 |
| “确认提示词，生成示例图” | 按确认内容生成独立预览，不能推断为批准修改代码 |
| “A 版更好” | 将 A 记录为当前会话的首选基线，后续只在授权范围迭代 |
| “按 A 方案修改这个页面” | 实施已明确的页面与方案，不重复请求同一批准 |
| “只改表格间距，其他保留” | 聚焦指定变化，不重做导航、配色或卡片结构 |
| “回到之前那版” | 指明目标版本并保留当前方案；修改实现时先核对目标及授权，不用破坏性恢复丢弃其他工作 |

已明确授权的工作持续有效。新增功能、迁移框架或改变整体方向需回到具体方案确认。直接要求更新 skill、制作独立预览或整理文档草稿属于对应范围的授权，不需生成无关 UI 示例图。

## 局部迭代与停止条件

反馈用“位置 → 问题 → 改法 → 保留内容”；交互用“动作 → 变化 → 结果”。先保留已认可的内容、主要数据、操作入口、视觉方向与组件语言，再改变一个主要因素，让前后比较有意义。

每次迭代说明要改善的可见问题。用户偏好原版、分组变模糊、操作更难发现、主要任务变慢或必须增加解释才能弥补时，停止继续删减并建议保留基线。不将更少颜色、卡片或动画本身当作成功指标。不覆盖历史文件，不把会话偏好自动写入长期记忆。

## 交付与验证

分别报告需求与提示词、视觉示例、代码实现、功能验证、部署和发布。保留关键字段、单位、权限、错误与操作结果；采用模拟数据要标明。静态图不能证明颜色值、字号、细边框、键盘、性能、业务数据或动效已经落实。

批准实现后按任务检查：主路径与失败恢复、加载与空状态、真实内容极值、窄屏、键盘焦点、触控与连续操作。只报告实际执行的验证，不用“已生成图片”替代功能验收。
