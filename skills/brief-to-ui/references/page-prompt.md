# 一句想法到页面生成提示词

## 什么时候使用

用户提出新页面、新产品或方向尚未确认的新需求时，先把简单想法整理成完整的页面生成提示词草案。用户负责判断是否符合意图，助手负责补齐结构、内容、交互与视觉约束。不要求用户学习提示词写法，也不先发一张空表让用户填写。

默认顺序：一句想法 → 必要研究 → 提示词草案 → 用户确认或修改 → 示例图 → 明确批准实现 → 实施与验证。提示词确认是独立步骤，不能直接跳到示例图或业务代码。

已经确认的提示词、用户给出的完整提示词及已批准的局部迭代可直接沿用，不重复请求同一确认。用户明确要求按给定提示词直接生成时执行对应交付；既有批准不因此扩大到其他页面、修改代码或部署。

## 草案必须可以直接使用

先用一句话说明理解的目标，再给一个可复制的完整提示词文本块。不要只输出关键词、占位符、让用户自行拼接的模板或未经解释的技术术语。一般单页以约 400–800 个中文字为起点，复杂度决定长度，不为凑字数添加功能。

提示词应覆盖：

1. **页面与人群**：产品类型、页面名称、使用者、设备与使用场景。
2. **任务与优先级**：一个主要目标、必要的次要任务、主操作和阅读顺序。
3. **内容与布局**：必要模块、字段、操作入口及分组关系。没有依据的业务模块作为待确认建议，不伪装成已有功能。
4. **内容依据与状态**：真实内容来自哪里；没有数据时明确采用模拟数据。需要哪些加载、空、错误、成功与权限状态，不虚构业务规则或权限。
5. **视觉与文案**：采用现有设计系统或已确认配置，把“高级”“简洁”等词转成可执行的字号、密度、颜色语义、对齐、容器与图标约束。默认规则见其他参考，不把整个 skill 原样堆进提示词。
6. **交互与适配**：写清“动作 → 变化 → 结果”，包含筛选、行操作等实际需要的反馈，以及窄屏组织原则。没有需求时不增加拖拽、动态图表或多级弹窗。
7. **交付与边界**：这次生成图片、交互原型还是实现代码；默认先生成一张独立示例图。写清尺寸或设备、保留内容、禁止扩展范围和可观察的完成标准。

生成约束是给模型的说明，不是要求放进界面的解释文案。静态图呈现选定状态；其他状态与交互规则可随图说明，不能声称图片已实现交互、精确色值或响应式行为。

## 事实、假设与缺口

在文本块外列出最多三个关键假设或待确认项，帮助用户快速纠偏；让会影响生成结果的假设在提示词内也可识别，避免复制后变成既定事实。能够合理推定的排版和组件细节主动建议；权限、金额口径、审批逻辑和真实指标不得代替用户决定。

只有缺口实质阻塞方案时才先问，每轮最多三个易懂问题。其余情况先给可编辑草案。参考研究说明来源、学习点与适用边界；无法核实的参考不能写成已验证依据。

## 给用户的收尾

明确说明下一步范围，例如：“确认这份提示词后，我会先生成一张示例图。你也可以直接指出要改的模块、文案或风格。”此时等待回复，不因沉默或未反对而生成。

用户补充内容后，把修改合入完整提示词，简短说明哪些内容变了；实质改变目标、模块或业务含义时再次确认受影响部分。不要让用户自己合并零散修订。用户确认只授权刚说明的交付，选择图片也不等于批准修改代码。

## 已有方案的局部迭代

用户只要求表格行距、按钮对齐等明确局部变化时，保留已确认的提示词与视觉基线，记录本次差异即可。不要重新整理整个需求、扩展功能或反复走全套确认流程。明显新增页面或改变核心目标时，更新对应提示词并确认新增范围。

完整的一句想法示例见仓库的 `examples/idea-to-prompt/README.md`；该示例是规则说明，不是独立模型实测结果。
