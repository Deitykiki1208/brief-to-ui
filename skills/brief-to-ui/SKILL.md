# Brief to UI

以用户任务决定结构，让简单想法经过参考研究、视觉确认和局部迭代，成为清晰、一致、可验证的界面。重点是中文业务后台；其他界面按任务适配，不将后台密度套到所有产品。配色与组件语言采用可替换的 Deityki 默认配置。资料来源与阅读范围见 [sources.md](references/sources.md)。

优先级：任务与数据正确 → 分组与操作清晰 → 层级与一致性 → 装饰克制。简洁不等于移除全部卡片；减少装饰不能损害分组、阅读与操作效率。用户已选择的方向作为本轮基线，后续优化需说明改善了什么，达不到更好效果时保留或回到基线。

## 核心约定

- 用户可以只提供简单想法。主动整理需求、研究参考并提出具体方案，不要求用户先写完整提示词或掌握技术术语。
- 读取用户提供的项目规范及已有设计系统；若项目根目录存在 UI_PROFILE.md，按 [profiles.md](references/profiles.md) 读取，不擅自创建或覆盖。后续明确指示优先，数值与默认库属于可配置偏好。
- 新的 UI 设计与布局调整先生成可审阅的示例图；重要动效补充可播放演示或交互原型。收到明确确认后才能修改业务页面代码、配置或目标文档。确认前可做只读研究和独立预览，不将提案混入目标文件。已有明确批准在范围内持续有效，不重复询问；实质改变范围时重新确认。用户明确要求更新本 skill 时按已授权范围更新，无需为规则文档制作 UI 示例图。
- 文案不用点号作装饰分隔，删除冗余说明和次要标签。保留任务所需的名称、错误原因和操作结果；使用面向实际人群、长度适当的成熟用语。默认不使用 emoji，统一使用开源 UI 图标。
- 未指定项目覆盖时，界面配色统一映射 Radix Colors 语义变量。每页优先三种字号、最多四种，最小 12px；普通边框与分隔线默认 0.5px。检查光学对齐、嵌套圆角和装饰的实际用途，详见视觉基础。
- 默认减少动效，保留必要反馈；需要过渡时以 ease-out、250ms 为调试基线。此规则替换早期强制所有前端具备进出动画、所有按钮缩放的偏好，Morph 仅用于有明确关联的元素。尊重减少动态效果设置，详见组件与交互。
- 新 React Web 项目默认以 shadcn/ui Nova、Radix Colors 和 Lucide 统一视觉；Motion、react-resizable-panels、dnd-kit、Zustand 按功能需要选用，详见资源路由。既有项目先核对兼容性与迁移范围，同一职责限制重复依赖。

卡片用于表达独立对象、独立操作或不同内容边界。先说明每一层容器的用途，再删除无意义的重复包裹；不把“少卡片”升级成“零卡片”指标。后台布局取舍见 [admin-patterns.md](references/admin-patterns.md)。

## 使用方式

根据当前请求选择必要参考，不要一次加载整个资源目录：

- 想法零散、方案确认、反馈或范围变化：读 [collaboration.md](references/collaboration.md)。
- 总览、列表、表单、详情、审批及卡片取舍：读 [admin-patterns.md](references/admin-patterns.md)。
- 使用其他人的配色、组件和密度偏好：读 [profiles.md](references/profiles.md)。
- 视觉设计、排版、配色、响应式：读 [visual-foundations.md](references/visual-foundations.md)。
- 表单、按钮、卡片、表格、浮层、状态与动效：读 [interaction-patterns.md](references/interaction-patterns.md)。
- 寻找参考、课程、组件或工具：读 [resource-routing.md](references/resource-routing.md)，再按当前任务访问相关原始来源。
- 解释依据、复核资料、研究新链接：读 [sources.md](references/sources.md)。

## 决策流程

1. 从上下文提炼用户与场景、当前痛点、最重要的 1–3 项任务、必须保留的内容和规则、本次交付物及可观察的验收标准。区分事实、建议、假设和待确认内容。仅对实质影响方案的缺口提问，每轮最多三个普通中文问题，优先提供易懂选项；一般细节主动建议，不编造业务规则、权限或真实数据。
2. 研究相关官方示例、成熟产品和优秀高 star GitHub 项目，通常选 3–5 个最相关参考，说明学习点与适用边界。复用足够的既有研究，简单修改不机械重复搜索。选型与研究规则见资源路由。
3. 先安排信息优先级、阅读顺序和主操作，提供合理默认值，将必要选择放在用户自然打算选择的节点。用分组、留白和结构减少说明文字及无意义确认；不将安全、权限和真实业务需要的确认当作可删除的装饰。
4. 将需求转成可审阅的视觉方案与关键路径，采用核心约定和当前平台能力，不自动添加玻璃、渐变、整页卡片或无关功能。按核心约定提供预览并等待确认，确认前不修改业务实现。区分“同意继续探索”“选择视觉方向”和“批准修改实现”，只在实际授权范围内推进。
5. 确认后完成授权范围内的实现与验证。以真实或清楚标注的示例内容检查长标题、数字、缺失内容、各状态及不同宽度。将方案、代码、验证、部署和发布状态分开报告。
6. 局部迭代沿用 Lovart 公开工作流程的启发：用途与参考 → 可查看首版 → 选定方向 → 指定位置修改 → 交付。反馈整理为“位置 → 问题 → 改法 → 保留内容”，交互整理为“动作 → 变化 → 结果”。保留已认可的方向，不无故重做整套设计；不声称已验证 Lovart 内部算法或生成质量。用户更喜欢原版时，承认偏好选择，先分析取舍，不强推更极端的简化或覆盖历史方案。

## 评审与交付

评审要指出位置、观察到的问题、对用户的影响和具体修改；把观察与推测分开。优先处理任务无法完成、内容无法理解和状态不清，其次检查冗余文案、颜色语义、字号数量、光学对齐、边框、圆角、动效必要性和重复依赖。评审发现问题不自动扩大已批准的修改范围。

设计方案应交代主次、排版、颜色用途、组件状态和关键适配规则。不要只提供形容词或孤立的颜色值。多方案仅在存在实质性方向差异或用户要求时提供。

代码实现延续已有约定，验证范围与改动相称。组件自称“accessible”不能代替整页焦点、标签、键盘与实际内容检查。

交付至少说明本次目标、发生的变化、保留的内容、可审阅成果、已验证与未验证事项。比较方案时保持业务内容与核心数据一致，标记生成示意图的偏差；一次偏好反馈不能证明对所有用户或模型都更优。

默认中文、简洁具体。完成修改后说明原因、修改部分和实际效果；普通设计问题直接解释理由，不虚构已修改或已验证。静态示例图只证明外观方案，不能作为交互、性能或可用性验证。

## 资料使用约束

- 分清用户确认的个人规范、外部标准、作者经验和本次设计选择。核心约定中的字号、边框、动效基线与默认库是用户偏好，不宣称为普遍标准；具体适配需有依据。
- 选择某个库进行实现时，核对当前官方文档、版本、支持平台和许可证；本 skill 的目录是日期快照。
- 课程介绍页只说明公开介绍。未访问的章节、付费内容和无法加载的示例不得写成已学完或已验证。
- 灵感截图可以帮助分析层级与构图；其转化率、易用性、键盘操作和移动端行为需要额外证据。
- 新增来源时保存自己的简短归纳与精确链接，不复制完整课程或第三方 skill。
