# 从一句想法开始

以下为预期协作方式的编写示例，尚非独立模型评测记录，也没有生成对应的新图片或业务实现。

## 用户只说

> 我想做一个主管用的后台首页，能很快看到待办和异常。

## 助手整理的目标

让主管打开首页后，先找到需要处理的事项，再进入具体记录；默认先设计桌面 Web 首页。

## 页面生成提示词草案 P1

```text
请生成一张中文业务后台首页的桌面视觉示例图，画面宽 1440px，内容可读，直接呈现页面，不加设备外框。使用者是业务主管，主要目标是快速发现待办与异常并进入处理。这次只生成独立图片，不修改业务代码。

先按“固定导航 → 页面标题与必要操作 → 待办及异常摘要 → 待处理列表”的顺序组织。摘要用于快速定位，列表承担具体处理。避免把所有内容拆成同样大小的卡片；保留真正有助于分组的容器，通过留白、对齐和字号区分层级。辅助趋势区仅在用户确认有需求后加入。

待处理列表暂建议包含事项、关联对象、类型、更新时间、状态与查看入口；具体字段尚待确认，不预设审批权限、异常分级或结算规则。没有真实数据，采用少量明确标记的模拟数据，覆盖长名称与缺失值，不把示例数字当作真实指标。主操作是查看并进入处理，页面不提供未经确认的直接审批功能。

暂采用 Deityki 默认配置：Radix Colors 语义配色，低噪声背景，强调色仅突出主操作与选中项，状态颜色有明确含义。使用 Lucide 风格的开源图标，不用 emoji；文案使用主管熟悉的业务用语，不使用点号作装饰分隔，不添加重复副标题或解释性段落。全页优先三种字号，最小 12px；细边框以 0.5px 为实现目标，注意光学对齐和嵌套圆角，避免装饰性色条与重阴影。

筛选任务类型后更新列表并保留筛选状态；点击查看进入该事项详情。图片只呈现默认状态，另外简要说明加载、无待办、筛选无结果与加载失败时的反馈。必要过渡以 ease-out、250ms 为起点，尊重减少动态效果设置。窄屏优先显示事项、状态与主操作，其余信息在详情中承载，不要求图片证明动效或响应式已实现。

验收重点：第一眼能找到待办与异常，列表信息足够判断下一步，主操作清楚，文本可读且分组有序。以上说明约束生成过程，不应逐段写进页面。
```

## 提请用户校正

- 暂按桌面 Web 设计；如主要在手机使用，应调整布局。
- 只知道待办与异常需求，列表字段是建议；业务类型和处理规则尚未确认。
- 暂用 Deityki 默认视觉配置，已有项目设计系统时优先沿用。

确认这份提示词后，下一步先生成一张示例图。用户可以直接回复“确认提示词，生成示例图”，或说“主要在手机使用，把更新时间换成截止时间”。助手负责合并修订，用户无需重新编写提示词。

## 不同回复的后续

| 用户回复 | 应执行的工作 |
| --- | --- |
| “先改成手机端，并突出临期事项” | 合并修改，给出更新的完整提示词并确认改变的范围 |
| “确认提示词，生成示例图” | 生成独立示例图，保留修改业务代码的确认边界 |
| “图片方向可以，待办区再紧凑一点” | 沿用基线，只迭代待办区预览 |
| “按确认的图片修改这个首页” | 在明确的页面与业务范围内实施并验证 |

提示词的完整要求见 [页面生成提示词](../../skills/brief-to-ui/references/page-prompt.md)。
